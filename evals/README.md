# Оценка качества

Порядок обратный интуитивному: **сначала ручной разбор ошибок, потом метрики**. Метрика, придуманная до того, как посмотрели на реальные ошибки, измеряет не то, что ломается.

## Шаг 1. Эталон

`registry_46.jsonl` — 42 фактические карточки Excel-реестра заказчика с исходной нумерацией до 46. Каждая содержит текст сути, проставленные человеком баллы К1–К6, вычисленный индекс, категорию и флаг эскалации. Это готовая разметка, которую надо только распарсить (задача T017).

Ограничение, которое надо называть вслух: 42 фактические карточки — не бенчмарк, а верхнеуровневая проверка на реальных данных заказчика. Запрос на расширение — OQ-08.

Формат строки:

```json
{
  "id": 1,
  "kind": "act",
  "identifier": "Законопроект CAS DRM (№ 1215252-8)",
  "doc_type": "Законопроект (внесён в ГД)",
  "stage": "Законопроект внесён, I чтение — осенняя сессия 2026",
  "source_url": "https://sozd.duma.gov.ru/bill/1215252-8",
  "text": "Обязательный переход операторов платного ТВ...",
  "gold_scores": { "К1": 3, "К2": 2, "К3": 3, "К4": 0, "К5": 0, "К6": 3 },
  "gold_index": 65.0,
  "gold_category": "Среднее",
  "gold_escalation": true,
  "gold_final_category": "Высокое"
}
```

## Шаг 2. Разбор ошибок (до написания проверок)

1. Прогнать фактические карточки реестра через пайплайн, сохранить полные трейсы: вход, промпт, ответ модели, вычисленный результат.
2. Прочитать глазами все расхождения с эталоном. Не агрегировать, не считать средние — читать.
3. Свободные заметки к каждому расхождению (open coding).
4. Схлопнуть заметки в 5–10 категорий отказов (axial coding).

Гипотезы о том, что найдётся, — но проверять надо, а не предполагать:

- занижение К6 «срочность» из-за неверного представления модели о текущей дате;
- завышение К1 на общеотраслевых материалах, где связь с компанией косвенная;
- потеря флага эскалации там, где условие сформулировано в материале не теми словами, что в методике;
- галлюцинация дат вступления в силу.

Разбор оформляется в `error-analysis.md` с примерами. Это рабочий документ, а не отчёт: он меняется после каждого прогона.

## Шаг 3. Метрики под найденные категории

| Метрика | Как считается | Порог |
|---|---|---|
| **Базовая ставка** | доля релевантных материалов в эталоне | публикуется всегда, рядом с любой другой цифрой |
| **Baseline большинства** | доля класса-большинства = accuracy тривиального классификатора | справочно; результат системы обязан его превосходить (SC-013) |
| Recall по «релевантно» | из фактически релевантных сколько найдено | ≥0,80 (SC-005) |
| Precision по «релевантно» | из признанных релевантными сколько действительно релевантны | ≥0,70 (SC-005) |
| Accuracy | доля совпадений `is_relevant` с `gold` (К1>0) | **не заявляется без базовой ставки** (SC-005a) |
| **Провалы критичного** | доля карточек `gold_final_category ∈ {Высокое, Критическое}`, получивших «Низкое» или «Незначительное» | **0** (SC-006) |
| Расхождение категории | доля карточек с расхождением более чем на одну ступень | справочно |
| MAE по критерию | средняя абсолютная ошибка отдельно по К1…К6 и Н1…Н4 | справочно, показывает, какой критерий чинить |
| Заземление, ступень 1 | доля утверждений, чья цитата не найдена в оригинале | справочно, метрика качества промпта |
| Заземление, ступень 2 | доля утверждений с настоящей цитатой, которая утверждения не подтверждает | справочно; это тот класс ошибок, что даёт 17–33% у коммерческих правовых ИИ |
| Незаземлённое в итоговом саммари | доля прошедших утверждений, не следующих из цитаты, по ручной разметке 50 материалов | 0 (SC-007) |
| Ошибочные объединения | доля кластеров, объединивших разные позиции | 0 (SC-008) |
| Доля невалидных ответов | ответов, не прошедших схему с первого раза | справочно, метрика качества промпта |

### Почему accuracy отдельно не заявляется

Большинство материалов в потоке для GS Labs нерелевантны. Значит, классификатор «всё нерелевантно» получит accuracy, равную базовой ставке нерелевантных, — и это будет честная, проверяемая и совершенно бесполезная цифра.

Именно на этой методологической ошибке построила и потеряла заявленную ценность FiscalNote: годами продавала предсказание прохождения законопроектов «с точностью более 94%» при доле принимаемых биллей в единицы процентов, не публикуя ни базовую ставку, ни precision, ни recall.

Поэтому: базовая ставка и baseline большинства печатаются в одной таблице с результатом, всегда. Отчёт без них считается недействительным.

**Провалы критичного важнее общей точности.** Заказчик назвал это ключевым условием: пропущенное регуляторное изменение стоит дороже, чем десяток лишних материалов в ленте. При конфликте настроек всегда выбирается вариант с нулём провалов, даже ценой падения общей точности.

## Шаг 4. Маховик данных

Правки пользователя в интерфейсе (FR-081) пополняют эталон: исправленный балл — это новая метка, поставленная экспертом. Выгрузка журнала правок в формат датасета — задача T058.

Так датасет растёт от использования, а не от отдельной кампании по разметке. К концу хакатона эталон будет больше исходных 42 фактических карточек.

## Что не делаем

- Не используем LLM-судью как защитный механизм — только как дополнительную справочную метрику. Заземление проверяется вхождением строки, детерминированно.
- Не генерируем синтетический датасет моделью: он измеряет согласие модели с самой собой.
- Не заявляем на защите цифру, полученную не на данных заказчика.
