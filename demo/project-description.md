# Описание проекта — промежуточная версия

**Проект:** Интеллектуальный центр PR/GR-мониторинга для GS Labs  
**Кейс:** ООО «Цифра» (GS Labs), ITMO AI Product Hack  
**Дата:** 03.09.2026  
**Статус:** артефакты проектирования готовы; рабочий прототип сбора и кластеризации Telegram-новостей запущен; полный продуктный пайплайн по спецификации в реализации

---

## 1. Краткая аннотация

Решение заменяет 3–4 часа ежедневного ручного мониторинга информационного поля на **10–15 минут утреннего разбора**. Система автоматически собирает отраслевые новости и НПА, формирует заземлённые саммари, оценивает влияние на конкретную компанию по методике заказчика (К1–К6 / Н1–Н4) и отдаёт ленту, отсортированную по индексу влияния.

Ключевое отличие от медиа-агрегаторов: материал оценивается не по «интересности», а по вопросу **«что это значит для нашей компании»**. Индекс влияния считает код по формуле заказчика; LLM выдаёт только баллы 0–3 с обоснованием. НПА живут отдельным досье со стадиями и историей оценок.

Целевой эффект: ~630 ч/год на специалиста + снижение риска пропуска критичных регуляторных изменений (ПП № 1937, CAS DRM, требования КИИ и др.).

---

## 2. Проблематика

| Как есть | Боль |
|---|---|
| Ручной мониторинг 3–4 ч/день | PR/GR-служба перечитывает десятки источников и перепечатывает Excel |
| Excel-реестр на 46 карточек | Долго заполнять, неудобно читать и править, не подходит руководителю |
| Саммаризация уже пробовалась | Автоматизации **сбора** нет — человек всё равно собирает материал руками |
| Brand Analytics и аналоги | Есть агрегация, нет оценки влияния на конкретную компанию и нет жизненного цикла НПА |
| Цена пропуска | Штрафы, исключение из реестра ПО, срыв сроков импортозамещения CAS/DRM, риски по КИИ |

Заказчик прямо противопоставил задачу медиа-мониторингу: «оно есть, но не решает основную задачу».

---

## 3. Актуальная постановка задачи

Построить прототип аналитического центра, который:

1. **Собирает** материалы минимум из 5 источников трёх типов: СМИ/RSS, сайты регуляторов, Telegram-каналы.
2. **Структурирует**: саммари 3–5 предложений, сущности (кто / что / когда / последствия), тип (новость / НПА), тематика.
3. **Заземляет** каждое утверждение саммари на оригинал (две ступени: вхождение цитаты + подтверждение смысла).
4. **Оценивает** влияние по методике GS Labs; нерелевантное не попадает в основную ленту.
5. **Отдаёт** ленту с фильтрами, поиском, ссылкой на оригинал и раскрытием баллов.
6. **Позволяет** править саммари и баллы без затирания правок автоматикой; вести досье НПА; переключать профиль компании.

**MVP для защиты (минимум):** лента с оценкой на эталоне + автосбор из пяти источников + измеренное качество релевантности + отрепетированное демо.

Спецификация: 7 пользовательских историй, ~50 FR, 13 SC — `specs/001-ai-monitoring-center/spec.md`.

## 4. Выбранное техническое решение

### Архитектурные принципы (конституция)

| # | Принцип | Смысл |
|---|---|---|
| I | Ценность = эффект для компании | Профиль GS Labs — вход оценки; шум не поднимается в ленте |
| II | Детерминированный индекс | LLM → баллы; код → ИВ/ИА, категория, флаги |
| III | Заземление на источник | Нет цитаты / нет подтверждения → утверждение отбрасывается |
| IV | Человек — редактор | Правки не затираются переобработкой |
| V | Две сущности | Новость (разово) ≠ НПА (досье до «в силе») |
| VI | Демо важнее архитектуры | SQLite, без auth, планировщик в процессе |

### Стек

| Слой | Технологии |
|---|---|
| Backend | Python 3.11+, FastAPI, SQLAlchemy (async) + SQLite, APScheduler, Telethon, pydantic v2 |
| Frontend (план) | React 18, Vite, TypeScript, TanStack Query, Tailwind |
| Сбор | Telethon (Telegram), feedparser (RSS), selectolax + trafilatura (веб/регуляторы) |
| LLM | OpenAI-совместимый клиент, structured output; основной + резервный провайдер |
| Инфра | Docker Compose; CI/CD на демо-сервер (`specs/002-deploy/`) |

### Три решения, определяющие продукт

1. **Индекс считает код, не модель** (ADR-0003) — объяснимость, воспроизводимость, покритериальный eval.
2. **Новость и НПА — разные сущности** (ADR-0002) — то, чего нет у медиа-мониторинга.
3. **Профиль компании — конфигурация** (ADR-0005) — смена профиля переоценивает ленту без правок кода (пилот «Триколор» и др.).

### Метод работы

Проект ведётся по **GitHub Spec Kit**: спецификация — источник истины, код производен от неё. Граница дорожек E1/E2 — OpenAPI-контракт.

## 6. Предварительные результаты

1. **Продуктовая ясность:** зафиксированы MVP, критерии успеха (SC-001…SC-013) и границы скоупа (без auth, без промышленной ИБ).
2. **Методика заказчика оцифрована** и сверена с отраслевым RegTech-каноном: критерии К1–К6 встречаются в зрелой практике (applicability × severity × urgency).
3. **Технический риск Telegram закрыт** выбором Telethon со StringSession (ADR-0008) — код прошёл прод в смежном проекте.
4. **Прототип сбора живой:** парсинг каналов, персистентность SQLite, кластеризация, API health/topics.
5. **Инфра демо:** compose + план автодеплоя на сервер под защиту.
6. **Измерение ещё впереди:** H-01 (релевантность ≥80%) не проверена на `registry_46` — это главный риск до финала.

## 7. Ограничения текущей версии

| Ограничение | Комментарий |
|---|---|
| Нет продуктового UI | Frontend по плану не создан; демо API/топиков — промежуточное |
| Модель данных прототипа (`Post`/`Topic`) ≠ целевая (`Item`/`Assessment`/`Act`) | Фаза 1.5 + Phase 2 в `tasks.md` |
| Кластеризация пересоздаёт топики (`_clear_topics`) | Нарушает принцип «правки не затираются» — T099 обязателен |
| Кластеризация одним вызовом на весь период | Не масштабируется — T100 (инкремент + эмбеддинги) |
| Только Telegram | RSS и регуляторы (СОЗД, regulation.gov.ru) ещё не подключены |
| Нет скоринга влияния и заземления саммари | Ядро ценности продукта — в очереди US1 |
| Нет эталонного прогона на 46 карточках | Нельзя честно заявить «80%» |
| Auth / нагрузка / ИБ | Вне скоупа хакатона осознанно |
| Аккаунт Telegram | Личный номер участника; для пилота у заказчика нужен служебный |
