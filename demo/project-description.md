# Описание проекта — финальная версия

**Проект:** Интеллектуальный центр PR/GR-мониторинга для GS Labs  
**Кейс:** ООО «Цифра» (GS Labs), ITMO AI Product Hack  
**Дата:** 07.09.2026  
**Статус:** решение работает целиком и развёрнуто на демо-стенде — http://185.56.162.154/. Сбор, саммари с двухступенчатым заземлением, оценка по методике заказчика, лента, досье НПА и дайджест доступны в интерфейсе. Качество оценки измерено на 42 фактических карточках реестра заказчика.

---

## 1. Аннотация

Специалист по связям с государством и общественностью тратит три-четыре часа рабочего
дня на ручной обход лент СМИ, порталов регуляторов, реестров законопроектов и отраслевых
телеграм-каналов. Это около 630 часов в год на человека. Существующие агрегаторы отвечают
на вопрос «что интересного произошло» — а специалисту нужен ответ на другой вопрос:
что из произошедшего касается его компании и требует действия.

«Интеллектуальный центр PR/GR-мониторинга» собирает материалы из пяти типов источников,
формирует по каждому саммари, где каждое утверждение подтверждено дословной цитатой из
оригинала, и оценивает материал по методике самого заказчика — К1–К6 для нормативных
актов и Н1–Н4 для новостей. На выходе лента, отсортированная не по дате публикации,
а по индексу влияния на конкретную компанию.

Ключевое архитектурное решение: модель выставляет только баллы от нуля до трёх
с обоснованием, а индекс влияния, категорию и флаги эскалации вычисляет код по формуле
заказчика. В контракте ответа модели полей «индекс» и «категория» нет вовсе — она
физически не может их вернуть. Благодаря этому оценка воспроизводима, объяснима
покритериально и правится пользователем: изменил балл — индекс пересчитался.

Заземление саммари проверяется в две ступени. Первая — детерминированная проверка кодом,
что дословная цитата содержится в оригинале. Вторая — отдельная проверка, что цитата
действительно подтверждает утверждение. На корпусе из 820 утверждений вторая ступень
отбраковала 8,2 %, которые первая пропустила бы: цитата в тексте есть, но утверждения
не подтверждает. Именно этот класс ошибок даёт 17–33 % у коммерческих правовых ИИ.

Нормативные акты ведутся не как разовые новости, а как долгоживущие досье: стадия
жизненного цикла, хронология событий, история оценок и график динамики влияния.
Смена стадии отправляет связанные материалы на переоценку, потому что юридическая
сила входит в критерий К2. Это то, чего нет у медиа-мониторинга, и то, ради чего
у заказчика вёлся Excel-реестр вручную.

Результаты измерены на 42 фактических карточках реестра заказчика, где баллы проставлены
человеком. Формула воспроизводит методику точно: индекс и категория совпали на всех 42,
включая случаи, где флаг эскалации поднимает категорию на ступень. Модель, выставляя
баллы самостоятельно, попадает в ту же категорию или соседнюю в 38 случаях из 42.
Полная обработка одного материала занимает 12,7 секунды и стоит четыре копейки.

Решение развёрнуто и работает на демо-стенде: http://185.56.162.154/. Что честно
не закрыто: точность фильтрации нерелевантного измерить на данных заказчика нельзя —
в его реестре нет ни одной нерелевантной карточки, и это первый вопрос, который мы
задаём заказчику дальше.

## 2. Проблематика

| Как есть | Боль |
|---|---|
| Ручной мониторинг 3–4 ч/день | PR/GR-служба перечитывает десятки источников и перепечатывает Excel |
| Excel-реестр с 42 фактическими карточками и исходной нумерацией до 46 | Долго заполнять, неудобно читать и править, не подходит руководителю |
| Саммаризация уже пробовалась | Автоматизации **сбора** нет — человек всё равно собирает материал руками |
| Brand Analytics и аналоги | Есть агрегация, нет оценки влияния на конкретную компанию и нет жизненного цикла НПА |
| Цена пропуска | Штрафы, исключение из реестра ПО, срыв сроков импортозамещения CAS/DRM, риски по КИИ |

Заказчик прямо противопоставил задачу медиа-мониторингу: «оно есть, но не решает основную задачу».

## 3. Актуальная постановка задачи

Построить прототип аналитического центра, который:

1. **Собирает** материалы минимум из 5 источников трёх типов: СМИ/RSS, сайты регуляторов, Telegram-каналы.
2. **Структурирует**: саммари 3–5 предложений, сущности (кто / что / когда / последствия), тип (новость / НПА), тематика.
3. **Заземляет** каждое утверждение саммари на оригинал (две ступени: вхождение цитаты + подтверждение смысла).
4. **Оценивает** влияние по методике GS Labs; нерелевантное не попадает в основную ленту.
5. **Отдаёт** ленту с фильтрами, поиском, ссылкой на оригинал и раскрытием баллов.
6. **Позволяет** править саммари и баллы без затирания правок автоматикой; вести досье НПА; переключать профиль компании.

**MVP для защиты (минимум):** лента с оценкой на эталоне + автосбор из пяти источников + измеренное качество релевантности + отрепетированное демо.

Спецификация: 7 пользовательских историй, ~50 FR, 13 SC — `specs/001-ai-monitoring-center/spec.md`.

## 4. Выбранное техническое решение

### Архитектурные принципы (конституция)

| # | Принцип | Смысл |
|---|---|---|
| I | Ценность = эффект для компании | Профиль GS Labs — вход оценки; шум не поднимается в ленте |
| II | Детерминированный индекс | LLM → баллы; код → ИВ/ИА, категория, флаги |
| III | Заземление на источник | Нет цитаты / нет подтверждения → утверждение отбрасывается |
| IV | Человек — редактор | Правки не затираются переобработкой |
| V | Две сущности | Новость (разово) ≠ НПА (досье до «в силе») |
| VI | Демо важнее архитектуры | SQLite, без auth, планировщик в процессе |

### Стек

| Слой | Технологии |
|---|---|
| Backend | Python 3.11+, FastAPI, SQLAlchemy (async) + SQLite, APScheduler, Telethon, pydantic v2 |
| Frontend | React 18, Vite, TypeScript; сборка попадает в образ backend |
| Сбор | Telethon (Telegram), feedparser (RSS), selectolax + trafilatura (веб/регуляторы) |
| LLM | OpenAI-совместимый клиент, structured output; основной + резервный провайдер |
| Инфра | Docker Compose; CI/CD на демо-сервер (`specs/002-deploy/`) |

### Три решения, определяющие продукт

1. **Индекс считает код, не модель** (ADR-0003) — объяснимость, воспроизводимость, покритериальный eval.
2. **Новость и НПА — разные сущности** (ADR-0002) — то, чего нет у медиа-мониторинга.
3. **Профиль компании — конфигурация** (ADR-0005) — смена профиля переоценивает ленту без правок кода (пилот «Триколор» и др.).

### Метод работы

Проект ведётся по **GitHub Spec Kit**: спецификация — источник истины, код производен от неё. Граница дорожек E1/E2 — OpenAPI-контракт.

## 6. Полученные результаты

**Формула воспроизводит методику заказчика точно.** 42 карточки из 42: индекс, базовая
и итоговая категории совпали, включая случаи, где флаг эскалации поднимает категорию
на ступень.

**Качество оценки измерено на данных заказчика** (`evals/results.md`):

| | Значение |
|---|---|
| Категория совпала или разошлась на одну ступень | 38 карточек из 42 |
| Провалы «Высокое/Критическое» в нижние категории | 1 при цели 0 |
| Схема НПА, среднее смещение | +0,02 — систематического занижения нет |
| Схема новостей, среднее смещение | −0,66 — занижает, хуже всего Н2 |

**Двухступенчатое заземление ловит именно тот класс ошибок, ради которого сделано.**
На 820 утверждениях: 89,1 % подтверждены обеими ступенями, 2,7 % отбраковала проверка
вхождения строки, ещё **8,2 % — проверка следования**. В этих 8,2 % цитата дословно
присутствует в оригинале, но утверждения не подтверждает; проверка подстрокой их
пропустила бы. У коммерческих правовых ИИ этот класс даёт 17–33 %.

**Стоимость и время измерены:** четыре копейки на материал целиком, медиана
обработки 12,7 с при цели SC-003 в 10–15 с. Поток 150 материалов в сутки —
около 2 100 ₽ в год. Для сравнения: верхняя граница штрафа по ФЗ № 295-ФЗ
для операторов цифровых платформ — 500 000 ₽.

**Модель выбрана замером, а не на глаз** (ADR-0010): `gpt-4o-mini` проигрывал по всем
осям сразу, включая ключевое для заказчика число провалов критичного — 3 против 1.

## 7. Ограничения

| Ограничение | Комментарий |
|---|---|
| Точность фильтрации не измерена | В реестре заказчика нет ни одной нерелевантной карточки: базовая ставка 100 %. Заявленные 80 % на этих данных неизмеримы в принципе — нужен размеченный набор с отрицательными примерами (OQ-08) |
| Новостная схема занижает | Среднее смещение −0,66 балла, MAE по Н2 равен 0,91. Отсюда единственный провал критичного |
| SC-006 не достигнут | Один провал критичного при цели ноль |
| Время выше границы SC-003 | 14–25 с на материал после перехода на рассуждающую модель: цена трёхкратного снижения провалов критичного, решение зафиксировано в ADR-0010 |
| Generic web-adapter | Для стабильного извлечения конкретных проектов НПА могут потребоваться source-specific доработки |
| Автосбор на стенде выключен | Демо показывает подготовленный срез: необработанные материалы попадают в ленту пустыми карточками, а обработка не успевает за сбором |
| Auth / нагрузка / ИБ | Вне скоупа хакатона осознанно |
| Аккаунт Telegram | Личный номер участника; для пилота у заказчика нужен служебный |

## 9. Дальнейшие планы по развитию

**Ближайший шаг — разметка с заказчиком.** Нужны 50 материалов, размеченных
«релевантно / нерелевантно», обязательно включая нерелевантные. Без отрицательных
примеров точность фильтрации измерить нельзя: в реестре заказчика базовая ставка
равна 100 %, и любой процент на таких данных не значит ничего. Это открытый
вопрос OQ-08, и он первый по приоритету.

**Затем — устранить занижение новостной схемы.** Среднее смещение по Н1–Н4
составляет −0,66 балла, хуже всего критерий Н2 «релевантность бизнесу»: модель
ставит ноль там, где эксперт видит связь через затраты, процессы или рынок.
Отсюда же единственный провал важного в нижние категории. Рабочее направление —
few-shot из карточек реестра с непрямой связью.

**Пилот на втором профиле.** Заказчик называл «Триколор» кандидатом. Профиль
компании вынесен в конфигурацию (ADR-0005), поэтому запуск на другой компании —
смена файла, а не переписывание кода. Это же проверяет главное продуктовое
допущение: система не привязана к GS Labs.

**Дальше по спецификации.** Открытых задач 17, ключевые: Telegram-источники
(нужен служебный аккаунт вместо личного), уведомления о критических изменениях
(OQ-11) и решение заказчика по OQ-15 — ставить ли потолок категории при нулевой
релевантности бизнесу.

### Как разграничены зоны

Границей служат контракты, зафиксированные до кодирования: `contracts/api.openapi.yaml`
между backend и фронтендом, `contracts/llm-contracts.md` между backend и слоем модели.
Благодаря этому дорожки не блокировали друг друга, а расхождение ручных типов
с контрактом стало ошибкой компиляции, а не сюрпризом у пользователя.

Изменение поведения продукта начинается с правки `spec.md`, затем задачи в `tasks.md`,
затем код. Ни одна строка не написана в обход этого порядка.
