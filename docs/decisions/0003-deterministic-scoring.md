# ADR-0003. Индекс считает код, LLM выдаёт только баллы 0–3

**Дата:** 2026-09-02 · **Статус:** принято

## Контекст

Кейс требует приоритизации «высокая / средняя / низкая». У заказчика уже есть работающая методика: К1–К6 с весами и формулой для НПА, Н1–Н4 для новостей, шкала категорий и флаги эскалации. Целевое качество — от 80% точности категоризации по важности, при жёстком условии: критичные материалы не проваливаются в «низкий».

## Решение

LLM получает текст материала и профиль компании и возвращает строго структурированный ответ: балл 0–3 по каждому критерию плюс обоснование на каждый балл. Итоговый индекс, категорию и флаги эскалации вычисляет код по формуле из `docs/scoring-methodology.md`: для НПА флаг делает итоговую категорию не ниже «Высокое», а «Критическое» остаётся «Критическое». Просить модель назвать категорию напрямую запрещено.

## Альтернативы

- **LLM сразу возвращает «высокий/средний/низкий».** Отвергнуто: невоспроизводимо, необъяснимо пользователю, невозможно измерить, где именно модель ошибается, и невозможно настроить под другую компанию без переписывания промпта.
- **Классическая ML-модель на размеченных данных.** Отвергнуто: разметки объёмом, достаточным для обучения, нет — есть 42 фактические карточки реестра с исходной нумерацией до 46.

## Следствия

Точность измеряется покритериально: видно, что модель, например, systematically занижает К6 «срочность». Веса и пороги меняются в конфиге без правки кода и без переобучения. Пользователь исправляет один балл, а не отвергает оценку целиком, и каждая такая правка становится эталонной меткой для eval-датасета.

Цена: два вызова модели на материал (саммари + оценка) вместо одного и более строгие требования к валидации JSON.
