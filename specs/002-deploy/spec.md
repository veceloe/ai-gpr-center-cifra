# Feature Specification: Автоматический деплой на демо-сервер

**Feature Branch**: `002-deploy` (ведётся в `main`; отдельная ветка не создавалась — инфраструктурная фича без пользовательских сценариев в продукте)

**Created**: 2026-09-03

**Status**: Draft

**Input**: «Задеплой на сервер, сделай это через Spec Kit и GitHub CI/CD». Сервер — один хост с root-доступом, назначение — живое демо на защите.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Пуш в main обновляет демо (Priority: P1)

Инженер вливает изменения в `main`. Через несколько минут демо-сервер работает на новой версии, никому не нужно заходить на него руками.

**Why this priority**: без этого каждая правка перед защитой — ручной SSH и риск сломать то, что работало.

**Independent Test**: изменить строку в `/api/v1/health`-ответе, запушить, увидеть новый ответ на сервере.

**Acceptance Scenarios**:

1. **Given** деплой включён переменной `DEPLOY_ENABLED=true`, **When** в `main` приходит коммит, **Then** запускается workflow, код доставляется на сервер, контейнер пересобирается и перезапускается.
2. **Given** деплой не включён, **When** в `main` приходит коммит, **Then** workflow не создаёт падающего запуска.
3. **Given** workflow запущен вручную, **When** он завершается, **Then** результат тот же, что при пуше.

---

### User Story 2 — Сломанная версия не считается задеплоенной (Priority: P1)

Если после перезапуска сервис не отвечает, workflow завершается ошибкой с логами контейнера, а не зелёной галочкой.

**Why this priority**: зелёный статус при мёртвом сервисе хуже отсутствия деплоя — команда узнает о проблеме на защите.

**Independent Test**: намеренно сломать импорт в `main.py`, запушить, убедиться, что workflow красный и в логах видна причина.

**Acceptance Scenarios**:

1. **Given** контейнер запущен, **When** `/api/v1/health` не отвечает 200 в течение 120 секунд, **Then** workflow завершается ошибкой и печатает `docker compose ps` и последние 100 строк логов.
2. **Given** на сервере нет файла `.env`, **When** workflow доходит до перезапуска, **Then** он останавливается с понятным сообщением, не пересобирая контейнер.

---

### User Story 3 — Сервер готовится один раз и без секретов в репозитории (Priority: P2)

Участник команды готовит новый сервер одной командой, а секреты — SSH-ключ, токены Telegram и LLM — никогда не попадают ни в репозиторий, ни в логи CI.

**Why this priority**: сервер может смениться; секреты в git — необратимая утечка.

**Independent Test**: выполнить `deploy/bootstrap.sh` на чистой Ubuntu, добавить ключ и `.env` по инструкции, запустить workflow вручную — деплой проходит.

**Acceptance Scenarios**:

1. **Given** чистый сервер, **When** выполнен `bootstrap.sh`, **Then** установлены Docker и compose-plugin, создан каталог приложения, открыт порт 8000, напечатан список ручных шагов.
2. **Given** репозиторий, **When** выполнен поиск по истории, **Then** в нём нет ключей, паролей и `.env`.

### Edge Cases

- Два пуша подряд — второй ждёт первого, а не деплоит параллельно (concurrency group).
- rsync не должен стирать `.env` и данные на сервере — они исключены явно.
- `context/` с материалами заказчика на сервер не доставляется: там нечему их читать, а лишняя копия — лишний риск.
- Секреты не заданы — понятная ошибка на первом шаге, до любых сетевых действий.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-201**: Система ДОЛЖНА запускать деплой при пуше в `main` и по ручному запуску.
- **FR-202**: Деплой ДОЛЖЕН быть отключён по умолчанию и включаться переменной репозитория `DEPLOY_ENABLED=true`.
- **FR-203**: Код ДОЛЖЕН доставляться на сервер без выдачи серверу доступа к репозиторию (rsync с раннера, не `git clone` на сервере).
- **FR-204**: Доставка НЕ ДОЛЖНА затрагивать `.env`, данные приложения и `context/`.
- **FR-205**: После перезапуска система ДОЛЖНА проверить `/api/v1/health` и при отсутствии ответа за 120 с завершиться ошибкой с логами.
- **FR-206**: Два запуска деплоя НЕ ДОЛЖНЫ выполняться одновременно.
- **FR-207**: Секреты ДОЛЖНЫ храниться только в GitHub Secrets и в `.env` на сервере; в репозитории и логах их быть не должно.
- **FR-208**: Первичная настройка сервера ДОЛЖНА выполняться одним скриптом, не содержащим секретов.
- **FR-209**: Приложение ДОЛЖНО стартовать без S3-конфигурации — выгрузка в S3 включается только при заданном endpoint.

### Key Entities

- **Секреты CI**: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY` — задаёт владелец репозитория.
- **Переменная CI**: `DEPLOY_ENABLED` — выключатель.
- **`.env` на сервере**: Telegram и LLM — задаёт участник команды на сервере.

## Success Criteria *(mandatory)*

- **SC-201**: От пуша в `main` до ответа новой версии на `/api/v1/health` — не более 10 минут.
- **SC-202**: Сломанная сборка даёт красный статус workflow в 100% случаев; зелёный статус означает отвечающий сервис.
- **SC-203**: Поиск по всей истории репозитория не находит ни одного секрета.
- **SC-204**: Новый сервер вводится в строй за 15 минут по `quickstart.md` без участия автора пайплайна.

## Assumptions

- Ubuntu на сервере; `bootstrap.sh` рассчитан на apt и репозиторий Docker.
- Деплой от root — принято ради скорости на хакатоне; отдельный пользователь с ограниченными правами описан как путь развития, не реализован (ИБ вне скоупа по конституции).
- Демо доступно по `http://<host>:8000` без TLS и домена — для защиты достаточно.
- Отката к предыдущей версии нет: при провале health-gate старый контейнер уже остановлен. Для хакатона принято; починка — новый пуш.
- Деплоится `news_parser` как есть до завершения фазы 1.5; после переноса в `backend/` меняются только пути в compose.
