# backend

Реализация по `specs/001-ai-monitoring-center/`. Код производен от спецификации: менять поведение — правкой `spec.md`, а не здесь.

## Запуск

Нужен Python ≥ 3.11.

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env          # заполнить LLM_API_KEY, при необходимости Telegram
export PYTHONPATH=.

python -m src.cli init-db
python -m src.cli seed-profiles     # повторно обновить профили из config/company_profile.yaml
python -m src.cli seed-sources      # повторно проверить 5 источников из docs/sources.md
python -m src.api.main              # http://localhost:8000/api/health; стартует scheduler
```

Без `LLM_API_KEY` сервис поднимается, лента и управление источниками работают, обработка материалов — нет. Это осознанно: демо не должно падать из-за отсутствующего ключа.
Для smoke-проверок с реальным env не запускайте API, если не нужна фоновая обработка: API lifespan стартует scheduler и warmup. Предпочтительны явные CLI-команды с `--limit`.

## Команды

| Команда | Что делает |
|---|---|
| `init-db` | создать схему, проверить scoring.yaml, загрузить профили и 5 источников |
| `seed-profiles` | загрузить профили компании (FR-050) |
| `seed-sources` | загрузить базовый набор источников (FR-001) |
| `collect [--source-id N]` | разовый сбор |
| `process [--limit N]` | обработать необработанное: саммари, заземление, классификация, оценка |
| `parse-registry` | собрать эталон из Excel-реестра заказчика в `evals/registry_46.jsonl` (T017) |
| `export-revisions` | выгрузить журнал правок в `evals/revisions.jsonl` как эталонные метки (T058) |
| `verify-formula` | сверить индекс, базовую категорию и итоговую категорию с реестром заказчика (T014) |
| `telegram-login` | однократная авторизация, печатает `TELEGRAM_STRING_SESSION` (ADR-0008) |

## Три решения, которые видно в коде

**Индекс считает код, не модель** (`src/scoring/formula.py`, ADR-0003). В контракте `ScoreResultRaw` нет полей `category` и `index_value` вовсе — модель физически не может их вернуть. Она выставляет баллы 0–3 с обоснованием, всё остальное вычисляется по `config/scoring.yaml`. Проверено: `verify-formula` сходится с Excel заказчика на 42 фактических карточках с исходной нумерацией до 46.

**Заземление в две ступени** (`src/pipeline/grounding.py`, ADR-0007). Первая — вхождение дословной цитаты в оригинал, детерминированная проверка кодом. Вторая — отдельным вызовом модели: следует ли утверждение из этой цитаты. Вторая нужна потому, что первой недостаточно: настоящая цитата, не подтверждающая приписанное утверждение, проходит поиск по тексту. Отбракованные утверждения сохраняются с причиной — пользователь видит счётчик неподтверждённого.

**Правки пользователя не затираются** (`src/pipeline/runner.py`, принцип IV). Поле с записью в журнале правок пропускается при переобработке. Саммари не перезаписывается, а версионируется: машинная версия остаётся в истории.

**Тип материала задаёт источник** (`Source.item_type`, FR-013). Для сайтов регуляторов по умолчанию используется `act`, для Telegram и СМИ — `news`. При сборе значение сразу копируется в `Item`; модель определяет только тематику и не может переключить схему оценки новости/НПА по тексту.

## Известные ограничения

- Фронтенда нет: если API запущен осознанно, проверять через `/docs` или curl.
- Досье НПА (US3) реализовано минимально: есть создание/отслеживание досье из
  материала и чтение `/acts`; смена стадий, ручные события и переоценка досье
  остаются отдельными задачами. Дайджест (US7) не реализован — маршрутов нет.
- Дедупликация (US6) есть на API: лента схлопывает дубли, `GET /stories/{id}`, `POST /stories/{id}/split`.
- `web`-адаптер собирает ссылки по типовым селекторам списков; для стабильного извлечения конкретных проектов НПА могут потребоваться source-specific доработки.
- Качество на живой модели и полный E2E статус не заявлены.
